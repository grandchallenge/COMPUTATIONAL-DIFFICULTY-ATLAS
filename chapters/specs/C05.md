# C05 — Reductions: Transporting Difficulty

Status: keystone specification v0.1

## Pedagogical objective

The reader should understand a reduction as a compiler or translator that lets a solver for one problem solve another, with directionality clear enough to reason about hardness correctly.

## Reader-facing question

If we had a solver for problem B, could we systematically use it to solve problem A?

## Core distinctions

- source problem vs target problem;
- many-one reduction vs informal resemblance;
- membership vs hardness;
- reduction direction vs hardness direction;
- asymptotic preservation vs practical runtime preservation.

## Anchor problems

- **SAT:** recurring reduction target.
- **Hamiltonian cycle / TSP decision:** concrete examples for reduction chains.
- **Halting:** later used to show the same reduction idea extends beyond resource-bounded classes.

## Formal payload

Primary notion:

\[
A \le_m^P B
\]

iff there exists polynomial-time computable \(f\) such that

\[
x\in A \iff f(x)\in B.
\]

Prove:
- transitivity by composition;
- if \(A \le_m^P B\) and \(B\in P\), then \(A\in P\);
- why a hard target inherits lower-bound consequences from source problems.

Introduce Turing reductions only as a contrast unless required later.

## Epistemic-status requirements

Every hardness statement names or makes unambiguous the reduction type and reference class.

## Exercises / thought experiments

1. Trace a reduction pipeline on a toy input.
2. Compose two stated reductions.
3. Spot the reversed inference in "A reduces to B, so A is harder than B."
4. Explain why a polynomial reduction may still be a poor practical implementation strategy.

## Map update

The reader replaces a scalar "hardness level" model with a directed relational model.

## Exit test

Given \(A \le_m^P B\), the reader can correctly state what follows from an efficient algorithm for B and what does not follow from an efficient algorithm for A.
